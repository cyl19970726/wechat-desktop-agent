# 架构：一个本地群频道

本期让已有 Codex 或其他 agent 通过 CLI 使用一个明确配置的普通微信测试群。`channel_id` 是本地 UUID，`account_binding_id` 是本地标签，均不是微信官方 ID。没有模型服务、MCP 服务、多群调度或客户群接入。[单群架构图](../.archify/architecture-single-group-channel-20261007-152801/single-group-channel.html)通过了自动门禁，并完成指定浅色截图的人工视觉检查；图本身不是桌面验收证据。

```text
现有 agent（生成候选文本）
    ↓ CLI：单群绑定 / read / page / parse-copy / 合成测试 send / pause
本地私有状态 ─── channel_id + session_id + SQLite outbox
    ↓ 限定目标、串行 desktop.lock
Mac 原生驱动 ─── 唯一前台窗口、精确标题、局部捕获、AX 草稿/控件
    ↓ OCR 行观察；发送前后核验
微信桌面客户端

另一路：手工选取、复制的原文 → parse-copy → 来源未核验的记录
离线组件：方向等信息已核验的 Bubble → 分页锚点 → 私有 TranscriptStore
目前尚无自动选择/复制 → 确认记录 → TranscriptStore 的可信连接。
```

## 已实现的边界

| 部件 | 已有实现 | 尚未证明或尚未连接 |
| --- | --- | --- |
| 单群 CLI | `init/status/doctor/read/page/parse-copy/send/pause/resume`；本地私有单群绑定、稳定 channel/session ID、JSON 状态码 | 本轮真实群读写；多群与后台订阅不支持 |
| 标题诊断 | `doctor` 仅检查配置标题区，返回失败阶段、精确匹配和实际置信度；不返回文字或授予读写许可 | 当前 CLI 实测在登录页因窗口门禁拒绝；持续捕获仍待通过 |
| 原生读取 | 桌面锁、唯一前台窗口与精确标题门禁、限定区域捕获、本地 OCR；`page` 仅滚动一小段并返回新视口 | 只产生 `direction=unknown` 的 OCR 行；未分消息、未识别发言者、无官方消息 ID、无可靠已读/去重 |
| 复制文本解析 | `parse-copy` 保留显示标签、分钟时间、完整正文和顺序；私有四条测试样本已核验 | 不读取系统剪贴板、不自动框选、不核实群来源或方向；不写确认日志 |
| 原生发送 | 检查草稿及按钮，输入和点击各自限定为一次；持久化尝试后执行，未知结果停住 | 严格 AX、锁屏状态、客户端布局与中文 OCR 现场能力尚未验收；未证明收件端送达 |
| Outbox | SQLite 状态机、每账号 lease/epoch、暂停接管、明确 `request_id` 幂等、点击前落盘 | 依赖驱动提供真实新鲜观察；OCR 指纹不可代替请求 ID，无法承诺服务器级恰好一次 |
| Transcript | 离线 `Bubble`/分页锚点/确认起点/本地事件存储；歧义和断档拒绝 | 不接受原始 OCR 行；尚未接入 CLI，也未形成持续会话上下文 |

CLI 返回的 `observed_at`、窗口身份和 `viewport_hash` 可为未来页间证据提供材料，但图片哈希不是消息 ID；当前 `read`/`page` 不会推进 transcript 游标或宣称完整历史。分页算法必须先从截图中可靠分出气泡、核方向与截断，再寻找唯一、足够强的重叠锚点。相同文字可能是不同消息；锚点不唯一或起点未确认时保持 `partial`，不能把最新一屏直接接到已确认日志。即使未来完成拼接，“连续”也只能相对用户确认的本地起点成立。

## 受监督 Computer Use 路径

另一路 Computer Use 工具在副屏完成了精确测试群与空草稿的画面核验，并用受监督的 `paste`/Return 做了一次合成事务尝试；它没有连接上述 CLI、原生驱动、outbox 或 transcript。原程序提交先出现本人气泡与等待指示；手机登录确认后，界面出现红色失败标志，另一身份明确反馈未收到，故**原提交失败**。用户之后独立手动重发：同一编号气泡的失败标志消失、时间改变，但收件端尚未再次核验，只能记为人工重试后的 `ui_observed`。这两个动作不能合并成一次成功发送。登录提示与提交时间接近，不能由此推断防御或其他原因。当前停止新发送及程序重试，只进行只读核验。这个路径适合短期受监督的界面试验，不能替代稳定消息身份、分页重建、私有持久游标、单账号串行发送和未知结果恢复。同一台 Mac 的主副屏共享键鼠焦点，不能用屏幕划分独立并行 UI owner。

用户手工框选后，复制快捷键已取得四条授权合成记录的本地原文，包含显示发言者、分钟时间、正文与顺序；真实私有样本通过 CLI 解析。CUA 自动框选仍返回辅助功能错误，跨页连续性未验证。因此现阶段可把原文复制作为受监督读取的入口候选，不能写成已实现的自动消息订阅器。方向、群来源、气泡截断与覆盖范围仍须视觉核验；时间标签和显示名不等于官方消息或成员 ID。

## 发送事务

`prepared → draft_verified → submit_attempted → ui_observed / failed / indeterminate → recipient_confirmed` 是本地证据层级。提交按钮前先持久化 `submit_attempted`；原生输入前还有单独的持久化尝试标记，以免崩溃后重复输入。重复 `request_id` 与相同文本返回旧状态，冲突文本拒绝；内容相同的两个独立请求可以使用不同 ID。暂停切到人工模式并使旧的 lease/窗口观察失效，不会清除已尝试消息。

当前 `send` 只允许显式合成测试，并把 `request_id` 放在可见测试文本前缀。将来处理客户消息时不能默认把技术编号写进回复；需要另行设计稳定请求身份与人工审核规则。CLI 不自行生成回复，也不把 OCR 文字送往模型或网络。

`ui_observed` 仅是本机界面观察。另一测试身份的独立收件证据才能支持 `recipient_confirmed`，这仍不等于微信官方服务器回执。界面失败、截图中断、输入状态未知或收件端无证据时，停止并交给人工判断，不自动重试。
