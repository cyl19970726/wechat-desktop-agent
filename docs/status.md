## 原生截屏路径的只读门禁

唯一前台微信主窗口在副屏时，辅助功能窗口与 CoreGraphics 窗口身份相符，整个窗口位于同一块显示器。对预先限定的标题区域，两种显示器局部过滤方式都返回原始像素全零，因此**该原生截图路径**门禁停止，没有捕获聊天正文。操作者短暂将同一窗口移到主屏后，原限定标题区域取得非零像素并由本地 OCR 识别出一行，但这行文字未通过目标测试群的**精确标题**核验，因此该路径仍未捕获正文、未翻页、未输入或发送。窗口随后已移回。另一个采用全局 `sourceRect` 的对照返回“capture unavailable”，未采用该路径。

这些观察只证明当前实测环境和**该原生实现**的副屏标题捕获尚未通过；不能推断副屏本质不受支持、微信有意阻止截图，也不能把主屏的一行 OCR 当作已读到目标群。该原生发送路径仍未有本轮真实尝试。

原生捕获改为对精确单窗生成系统 `CGImage` 后，先裁剪到指定区域，再绘制进仅该区域尺寸的私有像素缓冲区；不取整窗 data provider，也不回退全屏。新路径在副屏限定标题区域实际取得非黑像素，并精确识别目标标题字面，说明本次像素捕获已有进展。不过 Vision 置信度为 0.5，仍未通过既有 0.70 门槛；单中文/双语言校正和局部放大三组对照也未通过。因此**没有进入正文读取、分页、框选或发送**，不能记为 CLI 读取验收。小型非模态角标的已知几何与聊天窗口分别处理，移除了角标规则对旧主窗尺寸的硬绑定。

## 另一路受监督 Computer Use 试跑

随后使用操作者监督的 Computer Use 工具，**副屏**画面识别出目标测试群的精确标题、可见气泡和空草稿；微信的辅助功能树仍没有可用的消息或输入控件。独立的私有一次性记录先消费了编号，工具再用 `paste` 输入该 ASCII 合成文本；画面中的草稿与预期字面一致。执行一次 Return 后，界面出现本人气泡和等待指示。微信随后要求在手机上完成登录。用户手机确认后，CUA 截图看到这条新编号消息旁的**红色感叹号**，另一测试身份明确反馈**未收到**，因此原程序提交记录为失败，不再标为 `indeterminate`。

用户之后**手动点击重新发送**并报告可以了；后续画面中同一编号气泡不再有红色感叹号，显示时间也发生变化。这是独立的人工重试与本机界面观察（`ui_observed`），不改写原程序提交的失败记录；另一测试身份尚未对人工重试再次确认收件，不能写成送达成功。用户怀疑发送与账号退出/手机登录提示有关，目前只观察到时间接近及用户猜测，**没有因果证据**，不能归因于自动化防御。新发送和程序自动重试已停止，仅做只读核验。

这次 CUA 操作及用户手动重试**没有接入本仓库 CLI、原生驱动或 SQLite outbox**；程序提交使用私有的一次性尝试记录，不证明仓库 `send` 已可用。CUA 的坐标点击和按图像坐标拖选仍返回 AX 错误，程序自动框选未实现，也不再重复该尝试。Computer Use 可较快用于短期受监督测试，但长期会话仍需要已确认的分页记录、游标与去重，以及串行发送。同一台 Mac 的主屏和副屏共享键鼠焦点，不能把两个屏幕当作独立并行 UI 执行者。

## 用户手工框选的本地复制

用户在已核目标测试群手工框选四条已知纯文本合成记录；画面确认四个选框。CUA 发出复制快捷键后，剪贴板 `changeCount` 增加，本地 `NSPasteboard` 返回一个 195 字符、15 行的字符串。四条已知原文完整存在，顺序一致。每条呈“显示发言者标签一行、`YYYY年MM月DD日 HH:MM` 一行、原正文一行”，记录间为空行；当前证据提供显示标签、分钟级时间和文本，**没有微信消息 ID**。这批消息的 outgoing 方向另由画面核对，不能仅从复制文本推断方向、稳定发言者身份或时区。

私有样本经 `parse_copied_records(expected_count=4)` 及实际 `parse-copy` CLI 均得到四条、保留原文；同一副本重复 CLI 解析的结果一致。视觉核对方向后，同批次拼接不会重复追加，但**尚未确认历史起点**，因此没有推进长期会话日志。新增 CLI `parse-copy` 只解析调用者提供的文本，明确 `source_verified=false`、`coverage=provided_copy_only`、`history_complete=false`；它不调用系统剪贴板、不自动框选、不发消息，也不写入已确认 transcript。原始复制文本留在被忽略的私有目录，公开仓库只保留合成测试。跨屏/跨页复制、自动稳定选择及长期记录连续性仍未验证。CUA 画面曾返回全白帧，本轮又能看到正常测试群画面；这种间歇结果不能写成稳定截图能力。自动框选和新发送仍停止。

## 本轮监督下的原生键鼠复制

在用户现场确认测试群消息正常显示后，独立的一次性原生鼠标框选与 CUA 复制快捷键，使剪贴板产生新的文本。最初按四条预期拒绝；进一步核对格式发现五个时间头，并在本地把 PyObjC 桥接字符串转换为普通 Python 字符串后解析得到 **五条**记录、227 字符、19 行。五条正文全部与已知授权的合成消息匹配，实际 CLI `parse-copy(expected_count=5)` 保留了标签、时间和正文。预期四条却取得五条，因此**精确选择范围未通过**；方向也未由本次画面核验，不追加已确认日志。

该试验依赖用户当次群身份确认，使用私有脚本，**不是仓库 CLI 的自动微信采集能力**，也没有解除原生 0.70 标题门槛。随后多选状态下的全选快捷键仅复制出输入框内容，不提供历史读取证据；没有删除或发送该内容。主窗口仍会在 CUA 中变白，独立限定区域捕获又遇到全透明拒绝；用户肉眼确认消息正常，设置窗口截图、原生导航点击与滚动却可用。因此不能把一次标题像素或五条原文取得视为稳定图像捕获、分页或发送验收。设置保持不变，所有新操作均未发送消息。现场客户端为 Mac 微信 4.1.13、macOS 15.1；一次最小化/恢复实验已核窗口恢复，CUA 主窗口仍为白帧，未作为可用捕获方案。

## 历史 Mac 试验如何使用

在先前独立试验中，限定窗口截图和本地 Vision OCR 曾读到指定测试群的三条合成请求；原微信辅助功能消息树不稳定，截图也曾返回空帧，因此当时的入口在证据失效时停止。一次编号发送在准确输入并点击按钮后出现失败标志，另一测试身份确认未收到。另一次输入后截图失效，草稿未知，未点击发送。用户另报告过一次成功发送，但没有可关联到上述事务的完整编号与收件证据。这些相互不同的结果保持各自状态，不组合为“闭环成功”。它们只是本仓库设计输入，**不等于新原生驱动或 CLI 本轮已通过真实群验证**。

当前缺少微信服务器消息 ID 与回执、仓库自动执行路径中的实际登录账号独立核验、从 OCR 到可靠消息的提取、连续分页记录、长期无人值守运行和人机接管演练。使用桌面界面时，即使以后看见本机气泡，也需要独立收件证据才能说收件端已收到；不能承诺严格恰好一次送达。
